# 20260703 Raw-Latent Clustering Baseline

## Motivation

Every unsupervised result we currently trust (TFAP2 "mixture," PBX condensation) was fed
**classifier margins / multiclass probabilities**, which are clipped at class boundaries — a
distorted space. Because all of those results share that one distortion, their agreement was
never independent confirmation. We cannot currently distinguish soft-mixing (incomplete
penetrance) from a non-linear / >2D phenotype — both look identical after margin projection.

This folder builds a genuinely label-free baseline that clusters the **raw `z_mu_b` embedding**
directly, bypassing the linearity constraint. The question is empirical: does the raw latent +
its cross-bin connectedness extract *more* usable signal than the linearity-constrained
classifier? We do not pre-litigate this — we look.

Full design (motivation, null design, pass criterion): `docs/todos_scratch/unsupervised_raw_latent_baseline_idea.md`

---

## Strategy

- **Positive control first:** PBX is ~one phenotype direction, known-good. If the unconstrained
  method can't reproduce the known-good easy case, it's dead. Pass PBX → then TFAP2 (withheld).
- **The clustering method never changes.** It is always: features → UMAP init → trajectory
  condensation. There is no k-means or Leiden step anywhere. What *can* differ is only the
  **input to UMAP** — e.g. a distance matrix of raw z_mu_b distances, a kNN graph on the raw
  embeddings, or the classifier-margin space. The comparison axis is "what feeds UMAP," not
  "which clustering algorithm."
- **HTML render is the gate:** the condensation coordinates for each arm (raw z_mu_b vs. margin
  baseline) must render coherently into one self-contained HTML. If that fails, stop — the
  approach is not viable.
- **No force sweep:** non-degenerate + right emergence shape = done. The PBX margin condensation
  went down a sweep rabbit hole (`20260329`); we do not repeat that here.

## Scripts

0. **`0_load_pbx_latents.py`** — Load, normalize genotypes, bin 4 hpf. Outputs `tables/pbx_binned_zmub.csv`.

1. **`1_cluster_raw_latent.py`** — Run full trajectory condensation solver on the raw z_mu_b
   features using the same PBX config (sigma=0.5, epsilon_r=5e-4, elastic=16, attract_k=20,
   500 iters). UMAP init → condensation dynamics → `condensed_positions.npz` + standard viz bundle.
   Output: `figures/condensed_raw_zmub/`.

2. **`2_triptych_html.py`** ← **GATE** — Dumps the post-condensation coordinates directly into
   one self-contained Plotly HTML with three 3D panels (x, y, hpf), colored by genotype:
   (1) raw z_mu_b UMAP init, (2) raw z_mu_b condensed, (3) margin baseline condensed. Coords and
   plotly.js are embedded inline (no iframes, no external assets). Open `figures/triptych.html`.
   If this fails or looks degenerate, stop — do not proceed to null/discrepancy steps.

3. **`3_embryo_id_null.py`** — Embryo-ID-shuffle null (scrambles trajectory identity, keeps
   pooled marginal cloud byte-identical). Reclusters; renders as an additional HTML panel.

4. **`4_graph_and_discrepancy.py`** — Per time-bin: embryo-level connectedness graph for each
   method and null. Real-vs-null discrepancy per bin; graph-vs-graph agreement across methods.
   Aggregates into a curve.

5. **`5_discrepancy_heatmap.py`** — Renders discrepancy-over-time as a heatmap (emergence profile).

6. **`6_compare_to_margin_condensation.py`** — Pass/fail evaluation against the pass criterion;
   findings written here.

## Falsifiable prediction (stated before looking)

Real ≈ null at the earliest bins; real ≫ null at late bins.

A **large discrepancy at the earliest bins** would indicate leakage or the embedding encoding
batch/position rather than phenotype — the over-time shape self-validates the pipeline.

---

## Pass criterion

Discrepancy is **near-zero early and large late** (emergence shape), AND real PBX structure is
**visibly distinct from the null** at the bins where structure exists.

The bar is **non-degenerate, not "beats the margin/condensation method."** Disagreement with
the margin case is a signal, not a rejection.

## Findings

### PAUSED (2026-07-04) — batch effects, not a param/baseline bug

Baseline path and condensation params are both correct (see Data section; verified against the
final principal-tree run's `metadata.json` and the `--variant raw` generator). The gate HTML
(`figures/triptych.html`) renders fine. **But** the raw z_mu_b condensation shows **disjointed
vertical "columns"** over time instead of the coherent cross-time phenotype groupings we got before.

**Diagnosis (working hypothesis):** the raw z_mu_b latent encodes **experimental batch / experiment-
of-origin** alongside phenotype. The margin/classification baseline never showed this because the
**classifier effectively regresses batch out** — margins live in a phenotype-discriminative space
where batch is projected away. So the previously "coherent" cross-time groupings were partly *an
artifact of that batch correction*, not purely phenotype. There is still real structure in the raw
latent — it's just fragmented by batch rather than connected across time.

This reframes the folder's premise: the raw latent is **not simply "cleaner than margins."** It
trades margin-clipping distortion for batch contamination. Both spaces are compromised, differently.

**Why the fix is non-trivial (do NOT rush this):** batch and phenotype may be **partially confounded**
(genotypes not balanced across the 3 experiments). Naive batch regression / per-experiment centering
risks removing genuine phenotype signal along with batch — the same over-correction failure mode we
avoid with b9d2's heavy tail. Any batch-removal step needs a design that protects phenotype variance
(e.g. batch axis estimated on controls only, or a confound-aware method) and a check that it doesn't
flatten known-good PBX structure.

**Next (unstarted):** decide a batch-correction strategy for z_mu_b before re-running the null/
discrepancy steps (3–6). Steps 3–6 are on hold until then.
